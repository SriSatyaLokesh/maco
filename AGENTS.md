# AGENTS.md

Instructions for coding agents working **on MACO itself**. For using MACO on
another repository, you want the skills, not this file.

Human contributors: [CONTRIBUTING.md](CONTRIBUTING.md) is the full version.
This file is the machine-readable subset, kept deliberately short because it is
loaded on every session in this repository.

## Before you finish

```bash
npm run sync && npm run validate
```

Both must pass. CI runs the same two commands, so skipping them just moves the
failure to someone else's pull request.

## The one rule

**A skill is a prompt. Budget it like code, because it is code.**

Every skill states its own input limits. Carry that budget with any change. A
skill that reads a whole repository to review a diff has defeated the project.

## Never hand-edit these

| Path | Why |
|---|---|
| `.agents/skills/**` | Generated by `npm run sync`. CI fails on drift. |
| `.claude-plugin/marketplace.json` plugin list | Hand edits are fine, but the `source` must resolve to a directory containing `.claude-plugin/plugin.json` and a `skills/` directory, or the plugin installs zero skills. |
| `.github/workflows/maco-*.yml` | Consumer templates. They are validated for YAML syntax, never executed here. |

## Editing a skill

Source of truth: `plugins/maco/skills/<name>/SKILL.md`.

- Frontmatter `name` must equal the directory name.
- Frontmatter `description` is the only text a host reads when deciding whether
  to load the skill. Third person, imperative, trigger shaped. Under 1024
  characters. "Review a pull request" triggers; "This skill reviews pull
  requests" often does not.
- Do not rename the `code-review` directory. GitHub Copilot code review
  auto-loads skills from a review-focused directory name, and renaming it makes
  Copilot stop loading the skill silently.
- Body under 500 lines and about 5,000 tokens.
- Long detail goes in `references/`, with an explicit statement of when to read
  it. The mirror copies the whole skill directory, so sidecar files ship.
- State what the skill must never do. That is where most of the value is.
- No em dashes, no marketing tone, no exclamation marks.

## Conventions

- `gh`, `git`, `jq`. Nothing else. No MCP server, no vendor SDK, no runtime
  dependency. This is what makes 6-of-6 host portability real rather than
  aspirational, and it keeps `npm run validate` reproducible and free.
- Calibrate specificity per section. Prescriptive where a wrong order breaks
  something; explanatory where several approaches are valid and the agent should
  use judgement. Uniformly rigid is as wrong as uniformly vague.
- Add what the agent would not know. Do not explain what HTTP, a pull request or
  a GitHub milestone is.
- Markdown only. If it needs a renderer to read, it cannot be reviewed in a diff.

## Verifying a skill change

Use the `maco-skill-eval` skill, or reproduce its method by hand. Minimum: a
genuinely correct PR, a PR that skips exactly one AC, and a diff large enough to
exceed budget. The third case is the one that catches the failure mode that
matters: a confident partial review of code nobody read.

Run the whole case set, not just the case you changed. Regressions are the
failure mode worth hunting.

## Security constraints that are not negotiable

- `maco.json` holds roles and labels. Never a model name, a key, or a vendor
  endpoint. MACO does not make model choices.
- `pull_request_target` must never check out the PR head or execute code from
  the diff. It runs with repository secrets in scope.
- Provider keys go in repository **secrets**, not variables. Variables are
  visible in the Actions UI and leak through stray `set -x`.
- `failOpen: true` is deliberate. A budget stop degrades to a human comment, not
  a red X on a contributor's PR and not a silent pass.
- `budget.maxRunsPerDay` counts runs, not tokens. Do not describe it as a spend
  limit.
- No skill pushes to a contributor's branch. Suggestions are clicked by a human.

## Adding a label

Labels referenced by a skill, agent or workflow must be declared in `maco.json`
under `labels`. `npm run validate` cross-checks them, because a typo produces a
label that silently does not exist at runtime.

## Adding a dependency

Do not, without an issue first making the case. The scripts use only Node
built-ins, which is what keeps validation free and deterministic.
